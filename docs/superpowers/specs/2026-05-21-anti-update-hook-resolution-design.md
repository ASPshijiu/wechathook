# 抗更新 Hook 定位框架设计

## 背景

当前项目是面向微信的 LSPosed 模块，已具备最小 Kotlin 入口和微信进程 scope。下一步需要先建立抗更新基础能力，避免后续 Hook 点直接依赖固定类名或方法名后，在微信更新、混淆变化、局部重构时整体失效。

## 目标

第一阶段实现模块内部的抗更新 Hook 定位骨架：

- 对每个 Hook 点使用多候选特征匹配，而不是只硬编码单个类名或方法名。
- 按微信版本指纹缓存已解析结果，减少重复扫描成本。
- 在解析失败或低置信度时输出可诊断日志，方便后续分析新版微信。
- 保持框架轻量，不在第一阶段引入远程规则下发或自动 APK diff。

## 非目标

第一阶段不实现以下能力：

- 远程规则配置和在线更新。
- 自动下载、反编译、diff 新版微信 APK。
- 针对具体微信功能的大量 Hook 规则。
- 绕过微信安全机制、账号风控或服务端限制。

## 总体架构

框架由四个核心组件组成：

1. `VersionFingerprint`：读取微信包信息，生成当前微信安装版本的稳定指纹。
2. `HookResolver`：根据 Hook 点定义执行候选扫描、评分、排序和阈值判断。
3. `HookCache`：按版本指纹保存解析出的类名、方法签名和置信度。
4. `HookDiagnostics`：记录解析过程、候选得分、失败原因和最终选择。

模块启动后，微信进程进入 `onPackageLoaded`。框架先生成版本指纹，再查询缓存。缓存命中且结构校验通过时直接使用缓存结果；缓存缺失或校验失败时执行特征扫描。扫描完成后，如果最高分达到阈值，则写入缓存并返回目标；否则记录失败诊断，不安装该 Hook 点。

## Hook 点定义模型

每个 Hook 点应声明：

- 稳定 ID，例如 `chat_message_send`。
- 目标类型，例如类、构造函数、实例方法或静态方法。
- 候选扫描范围，例如指定包名前缀或已知入口类附近。
- 多个可评分特征，例如参数数量、参数类型、返回类型、字段结构、字符串常量、调用链、修饰符。
- 最低通过分数和可选的强约束。

强约束用于排除明显错误目标，例如包名不属于微信、参数数量不匹配、返回类型完全不兼容。可评分特征用于在多个候选之间排序。

## 版本指纹

版本指纹第一阶段使用以下信息组合：

- `packageName`，固定为 `com.tencent.mm`。
- `versionName`。
- `longVersionCode` 或兼容 API 的版本号。
- APK 路径。
- APK 文件 `lastModified`。

这些信息足以区分常见微信版本更新和重新安装场景。后续如有需要，可以加入 APK digest，但第一阶段不默认计算整包哈希，避免启动成本过高。

## 缓存策略

缓存以版本指纹为 key，Hook 点 ID 为子 key。每条缓存记录包含：

- 解析出的类名。
- 方法名和参数类型列表，或构造函数参数类型列表。
- 上次解析置信度。
- 框架版本号。

读取缓存后必须做轻量校验：类能加载、方法能反射找到、参数数量和类型仍匹配。校验失败时丢弃该缓存并重新扫描。

第一阶段缓存存放在模块可访问的私有配置位置。若 LSPosed 上下文限制导致无法写入，则框架退化为只扫描不缓存，但仍输出诊断日志。

## 诊断日志

诊断日志需要帮助定位“为什么某个 Hook 点没装上”。每次解析至少记录：

- 微信版本指纹。
- Hook 点 ID。
- 是否命中缓存。
- 候选数量。
- 前几个候选的分数和命中特征摘要。
- 失败原因，例如无候选、最高分低于阈值、反射校验失败。

日志只记录结构化技术信息，不记录用户聊天内容、联系人、账号信息或消息正文。

## 工具链建议

人工分析和验证使用以下工具：

- `jadx-gui`：主要用于阅读反编译 Java/Kotlin 结构、字符串常量和调用链。
- `apktool`：用于查看资源、Manifest 和 smali 结构。
- `Frida`：用于运行时验证候选方法是否被调用。
- `Bytecode Viewer` 或 `CFR`：作为 jadx 结果不清晰时的备用反编译工具。
- `ripgrep` 和脚本：用于批量搜索反编译目录中的字符串、类名和调用特征。

## 错误处理

Hook 解析失败时不应让微信进程崩溃。框架应跳过失败 Hook 点，记录诊断，并继续尝试其他 Hook 点。单个 Hook 点的失败不能影响模块整体加载。

如果某个 Hook 点的候选置信度低于阈值，默认不安装 Hook，避免误 Hook 到不相关方法造成不可预测行为。

## 测试策略

第一阶段以纯 Kotlin 单元测试覆盖框架逻辑：

- 版本指纹生成稳定。
- 缓存命中、缓存校验失败和缓存失效路径正确。
- 候选评分能按特征命中情况排序。
- 低于阈值时返回失败。
- 诊断信息包含必要字段且不包含敏感内容。

真实微信环境的验证留到具体 Hook 点实现后进行，使用 LSPosed 日志和 Frida 辅助确认。

## 后续扩展

当本地框架稳定后，可以按需要扩展：

- 远程规则下发，用于不发新版 APK 时修复 Hook 特征。
- APK diff 报告，用于对比新旧微信版本的类结构和字符串变化。
- 更强的特征类型，例如方法调用图、字段访问模式、局部常量组合。

这些扩展依赖第一阶段的 Hook 点定义模型、缓存模型和诊断模型，不应提前进入第一版实现。
